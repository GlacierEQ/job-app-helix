# Portfolio Expansion Map

## Decision surface

The candidate presentation uses two deliberately different repository scopes:

- **Recruiter-readable projection — 67 repositories at the July 31 snapshot.** This is a source-aware audience view with one Helix control-plane root plus sixty-six recorded child repositories. It is not a ceiling on the public system, the candidate set, or the broader engineering estate; each repository retains its own proof state.
- **Owner-accessible library snapshot — 1,171 repositories on July 31, 2026.** This records the authenticated inventory observed at that time. Ownership alone does not establish authorship, originality, quality, deployment, security, or recruiter relevance.

This separation keeps the hiring story strong without hiding the scale and diversity of the wider library.

## Four-layer repository mesh

### Layer A — Source-bound evidence

Repositories already admitted into the recruiter portfolio or priority spine through an explicit governance decision. Claims must cite repository-native tests, builds, documentation receipts, or deployment evidence.

Representative anchors include Job-App Helix, Resume Shapeshifter, AKOS, the Tower of Babel, Job Application, Pro-Code, Mastermind, and the Agent Coordinator candidate track.

No candidate-expansion repository is counted as verified recruiter evidence merely because it exists.

### Layer C — Supporting capability and upstream context

Frameworks, tools, educational materials, integrations, mirrors, and reference implementations may demonstrate breadth of study or provide implementation capability. They are not presented as original authored products without a verified delta.

Examples of capability families visible in the library include MCP tooling, retrieval systems, browser agents, local inference, document intelligence, digital forensics, mobile orchestration, cloud infrastructure, editors, and workflow platforms.

### Layer D — Private, sensitive, archived, backup, and excluded

Private case systems, confidential workstreams, archived forks, `Z-BACKUP-*` repositories, `*__public_fork_archive` repositories, test repositories, and placeholder templates remain outside the public recruiter story by default.

Their exclusion protects privacy and prevents inflated portfolio claims. A useful component can move into the recruiter surface only through a separate sanitized exhibit and evidence review.

## Promotion spiral

A repository moves toward recruiter use through this monotonic path:

1. **DISCOVER** — establish identity, visibility, default branch, and purpose.
2. **CLASSIFY** — distinguish original system, customized fork, upstream mirror, backup, sensitive work, or experiment.
3. **COMPARE** — identify the candidate's actual technical delta and unique value.
4. **PRESERVE** — protect useful branches, receipts, and provenance before cleanup.
5. **VERIFY** — run repository-native lint, tests, builds, security checks, and documentation gates.
6. **PROMOTE OR EXCLUDE** — add a source-bound claim or preserve the repository outside the hiring surface.
7. **RECEIPT** — record the evidence state and exact source revision.

## Recruiter interpretation

The tactical signal is not “1,171 production systems.” The signal is the ability to create and operate a governed portfolio architecture across a very large, heterogeneous library while maintaining strict boundaries between verified products, active candidates, supporting research, and excluded material.
