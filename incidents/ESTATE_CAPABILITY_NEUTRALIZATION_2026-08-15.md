# Estate Capability Neutralization Incident — 2026-08-15

Status: **ACTIVE RECOVERY**

The estate has entered recovery mode for a systemic failure pattern: repository repair/governance work repeatedly converted unfinished or ambitious capability into bounded local, synthetic, report-only, receipt-only, proposal-only, or proof-only surfaces. Verification controls became product ceilings.

## Governing correction

The approved product capability is the unit of completion. Governance, proof, security, provenance, and public-truth layers exist to make capability trustworthy; they do not replace capability.

When a public claim outruns implementation, the default engineering response is:

1. preserve the implementation lineage and experimental mechanisms;
2. mark only the unsupported projection as unproven;
3. build the missing implementation toward the intended capability;
4. retain later bug/security/provenance improvements;
5. verify the strengthened product at exact current head.

The default response is **not** to redefine the repository downward until its tests are easy to satisfy.

## Recovery rule

Every active canonical repository must be compared against its strongest legitimate prior capability state. Any removed/disabled path must be classified as:

- unsupported claim only;
- duplicate/superseded mechanism;
- unsafe unbounded path requiring a controlled authority gate; or
- real capability regression.

Real capability regressions are restored or completed on fresh canonical ancestry. Old source bytes and provenance remain preserved. A repository is not recovered until its canonical capability is at least as strong as the strongest legitimate prior state, while keeping later correctness and security gains.
