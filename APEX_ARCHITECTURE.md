# APEX Job-App Architecture

## Purpose

Job-App Helix demonstrates how independently useful systems become more valuable when composed, verified, and presented through one proof contract.

| Pillar | Representative systems | Question |
|---|---|---|
| Cognitive OS | AKOS, pro-code, token discipline | How is agent work governed? |
| Compute Physics | Cooling, energy, GPU health | Are physical constraints preserved? |
| Aerospace Software | Orbital, telemetry, launch, ground/mesh | Can domain outputs drive operational gates? |
| Reasoners & Safety | KV pressure, tasklets, mesh, monitors | Does the system fail closed? |

Company-aligned repository names identify problem domains and demonstration targets. They do not claim employment or deployment.

## Chassis

1. **Pistons:** runnable local units.
2. **Helix pairs:** Alpha truth/build plus Omega verification/ops.
3. **Campaigns:** multi-star compositions with a final decision.
4. **Proof contracts:** declared pain, executable evidence, and a green/failing result.

> **DONE iff proof(pain) is green.**

Maps, hashes, and diagrams support a proof; they do not substitute for one.

## Runtime layers

### L0 — Public fixture runtime

Standard-library Python, deterministic inputs, GitHub Actions, JSON receipts, recoverable faults, and terminal fail-closed behavior.

### L1 — Repository demonstrations

Strong individual repositories with their own tests and assumptions, linked rather than copied into this control plane.

### L2 — Workspace integration

Multi-repository runner, configured roots, optional local state, and operator-machine evidence.

### L3 — External deployment

Not claimed. Production would require a named target, threat model, observability, release ownership, service objectives, and deployment receipts.

## Public boundaries

The public hire repository excludes legal and family-case systems, private evidence, generated IDE memory, secrets, absolute workstation links, and employer-affiliation claims.
