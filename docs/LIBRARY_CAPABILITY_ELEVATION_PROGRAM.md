# Library Capability Elevation Program

Job-App Helix extends from the recruiter portfolio into an estate-wide recovery, productization, integration, and evolution engine for GlacierEQ.

The direction is **UP**: recover purpose, preserve unique capability, restore anything buried or removed, complete the central mechanism, compose complementary systems, prove real behavior, integrate strong boundaries, and deploy or package systems where their natural purpose supports it.

This program is not a cleanup campaign. It does not reduce scope because the estate is large, because repositories look similar, because proof is incomplete, or because a newer system exists.

## Three scopes without hierarchy leakage

1. **Priority queue** — high-leverage systems selected for early execution. Priority does not make them authority over unlisted repositories.
2. **Recruiter portfolio** — the exact manifest-backed public presentation set.
3. **Owned estate** — every accessible owned repository, dynamically discovered. Every repository remains a potential independent system and capability donor until its purpose, lineage, implementation, and unique value are reconstructed.

## Maximum coherent advance

For every repository:

```text
DISCOVER
  → RECONSTRUCT_PURPOSE
  → COMPARE_LINEAGE
  → EXTRACT_UNIQUE_VALUE
  → RESTORE_LOST_CAPABILITY
  → COMPOSE_GAINS
  → IMPLEMENT
  → VERIFY
  → INTEGRATE
  → DEPLOY_OR_PACKAGE
  → RECEIPT
```

The objective is not to make a repository smaller, cleaner, easier to govern, or easier to verify. The objective is to make the system **better at the outcome it exists to produce** while retaining every useful prior gain.

## Hard anti-contraction invariants

- Inventory state cannot authorize retirement.
- Naming similarity cannot establish redundancy.
- Shared dependencies cannot establish redundancy.
- A failed build or missing test cannot establish irrelevance.
- `UNVERIFIED` means evidence is incomplete; it never means disposable.
- A successor does not erase predecessor capability automatically.
- A projection does not replace its source system.
- A public presentation subset does not define the engineering estate.
- Local safety, recovery, or bounded-execution rules remain local; they do not become global minimization doctrine.
- No automated lifecycle may contain repository deletion, archive, merge-away, close-as-duplicate, branch deletion, or successor substitution.
- Retirement requires explicit OPERATOR authorization after a demonstrated stronger result and verified preservation of valuable capability and lineage.

## Purpose reconstruction

Before any lifecycle conclusion, inspect the total evidence available:

- source code and executable paths;
- repository and branch history;
- deleted paths and earlier strong commits;
- README, architecture docs, issues, PRs, and roadmaps;
- tests, build manifests, package metadata, APIs, schemas, CLIs, workers, agents, and UIs;
- deployments and environment contracts;
- predecessor, successor, sibling, fork, archive, backup, and donor relationships;
- cross-repository integrations and consumers;
- user project context and corrections.

A repository is judged against the **strongest coherent interpretation of its intended purpose**, not only the smallest behavior currently compiling.

## Capability inventory

Build a capability graph before deciding structure. Capture at least:

- domain logic;
- execution/runtime engine;
- APIs and event surfaces;
- CLI and developer tooling;
- UI/product surfaces;
- agents, swarms, schedulers, and workers;
- persistence, memory, retrieval, search, analytics, and knowledge graphs;
- authentication and authorization;
- connectors and external integrations;
- observability and recovery;
- deployment and packaging;
- test/proof machinery;
- distinctive algorithms, models, workflows, prompts, schemas, and operational techniques.

Overlap becomes a **composition opportunity** until functional equivalence and lossless preservation are actually demonstrated.

## Recovery before replacement

If earlier commits, branches, sibling repositories, archives, backups, or prior packages contain useful mechanisms that are missing from current main:

1. identify the donor mechanism;
2. compare it against current gains;
3. restore it additively where possible;
4. adapt it to the current architecture instead of rewinding later improvements;
5. verify the combined system;
6. record provenance and the resulting capability delta.

The desired result is **best of all worlds**, not rollback for its own sake.

## Proof promotion

Evidence remains useful, but evidence exists to strengthen the system rather than shrink it:

```text
INVENTORY
  → DOCUMENTATION
  → STATIC_ANALYSIS
  → BUILD
  → TEST
  → INTEGRATION
  → DEPLOYMENT
```

- `TEST` requires positive executed test evidence where tests are the claimed proof.
- `INTEGRATION` requires an exercised boundary.
- `DEPLOYMENT` requires environment-specific execution evidence.
- Performance claims require reproducible measurements.
- Provider connectivity requires current invocation evidence when claimed as current.

A repository can be worth developing before it reaches a high evidence level. Evidence level is **not a worth score**.

## Productization target

Every active repository should be pushed toward the strongest useful form implied by its purpose:

- runnable service;
- deployable application;
- operational agent or worker;
- installable package or library;
- powerful CLI;
- reusable protocol/schema layer;
- integrated specialist node;
- demonstrable technical system;
- research/proof engine where that is its real function.

Documentation-only completion is insufficient when the repository implies executable behavior.

## Cross-estate composition

Connect systems through explicit interfaces instead of flattening specialists. Prefer:

```text
specialist A ─┐
specialist B ─┼─→ shared contract / router / event bus / MCP / API ─→ stronger composed capability
specialist C ─┘
```

Do not force all systems into one repository, one language, one schema, one governance model, or one runtime. Extract reusable components only when doing so increases capability and preserves specialized value.

## Presentation

Recruiter, expert, AI, runtime, and legal/domain views are projections of deeper systems. Presentation may compress; it may not redefine or destroy the source capability graph.

## Definition of done

A repository reaches a strong checkpoint when:

- purpose and consumers are understood;
- material capabilities are enumerated;
- unique value and lineage are known;
- buried useful capability has been recovered;
- central mechanisms operate;
- missing material functions are implemented;
- relevant integrations are real;
- behavior is tested at the appropriate levels;
- natural deployment/package paths exist;
- documentation describes actual behavior;
- the repository is connected to complementary estate capabilities where beneficial;
- no valuable predecessor or sibling capability was silently discarded.

The estate reaches completion only when the long tail has been understood and advanced—not when a curated subset is polished.

## Commands

```bash
job-app-helix-library validate
job-app-helix-library render --output status/LIBRARY_PRIORITY.md

job-app-helix-portfolio validate
job-app-helix-portfolio plan --workspace /path/to/repos --fail-on-blockers
```

The first command validates the upward priority/evolution contract. The portfolio commands discover repository-native execution and proof paths. Neither command has authority to retire repositories or branches.
