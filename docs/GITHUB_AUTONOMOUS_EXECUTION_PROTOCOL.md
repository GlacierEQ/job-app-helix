# GitHub-Native Autonomous Execution Protocol

This protocol implements the Frontier Repository Innovation Engine constitution without replacing it.

## State machine

`DISCOVERED -> CENSUSED -> LINEAGE_RESOLVED -> BASELINE_VERIFIED -> BOTTLENECK_SELECTED -> ENVIRONMENT_MODELED -> RESEARCHED -> HYPOTHESES_EVALUATED -> EXPERIMENTING -> IMPLEMENTED -> VERIFIED -> ADVERSARIALLY_REVIEWED -> PROMOTION_READY -> CANONICAL -> MONITORED`

Escape states: `BLOCKED`, `QUARANTINED`, `SUPERSEDED`, `ARCHIVED`, `NO_ACTION_JUSTIFIED`, `EXPERIMENT_FAILED`.

A failed experiment is valid engineering intelligence. It must never be promoted as capability.

## Execution contract

1. Establish exact repository identity, branch, HEAD, status, tests, CI, releases, relationships, and current proof.
2. Classify the repository before investing in it. Do not independently modernize superseded lineage copies.
3. Baseline existing behavior before mutation and separate pre-existing failures from introduced failures.
4. Establish a consequential bottleneck and its root cause before feature work.
5. Model machines, software, organizations, economics, humans, and scale as an evidence-bound environment artifact.
6. Research obvious alternatives, standard practice, primary technical sources, and unresolved questions before asserting novelty.
7. Form multiple falsifiable hypotheses when uncertainty warrants competition; score them from explicit rationale references rather than invented confidence.
8. Run a novelty review against wrappers, renamed standard functionality, superior libraries, asymptotics, failure behavior, operational-step removal, and measurable effect.
9. Build the smallest valid experiment on an isolated, reversible change surface.
10. Enforce expected-head protection before canonical mutation. Stale analysis must be reconciled.
11. Model relevant failure scenarios and the observability needed to detect, explain, contain, and recover from them.
12. Verify using the strongest relevant ladder and choose tests capable of disproving the claim.
13. Adversarially attack the candidate and repair, limit, or invalidate it.
14. Emit machine-readable evidence for every material claim.
15. Apply the promotion gate. Passing CI alone is insufficient.
16. Generate recruiter, master-engineer, machine, and evolution surfaces from evidence.
17. Preserve a content-addressed run receipt.
18. Update the estate graph and reprioritize the estate by expected engineering leverage.
19. Continue upward through the bottleneck hierarchy rather than repeatedly optimizing solved layers.

## Autonomous authority boundary

Exploration is aggressive; canonical promotion is disciplined. Inspection, modeling, research, experiments, benchmarks, tests, adversarial review, evidence generation, and candidate preparation may proceed autonomously within available permissions. Irreversible, externally consequential, security-sensitive, deployment-sensitive, or governance-sensitive actions remain bounded by repository policy and the operating environment.

## Estate priority model

Priority is deterministic and evidence-bound. Favor consequential bottlenecks, strong repository fit, proofability, cross-repository compounding, enterprise relevance, and expected value. Discount implementation cost, regression risk, and uncertainty. Do not traverse repositories alphabetically or optimize for activity volume.

## Competing-hypothesis tournament

Do not psychologically commit to the first invention. For a material bottleneck, generate competing candidates when the solution is uncertain; reject weak ideas before implementation. Record why a candidate survived or died. Negative results are reusable estate intelligence.

## Promotion principle

A candidate becomes canonical only when the baseline is preserved, the selected bottleneck is actually addressed, the central mechanism exists, important invariants hold, relevant failure and observability models exist, meaningful failure paths are exercised, claims match evidence, limitations are explicit, and the change remains understandable and reversible where appropriate.
